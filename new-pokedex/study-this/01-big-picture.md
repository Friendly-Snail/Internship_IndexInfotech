# 1. The big picture

## What the old app looked like

The old app (`../pokedex`) was **two programs sharing one Bun server**:

```
                         Bun.serve  (src/server.ts + src/http-server.ts)
                                     │
            ┌────────────────────────┴─────────────────────────┐
            │                                                  │
   /ui  →  Bun's HTML bundler                       everything else → Hono app (src/app.ts)
           src/frontend/index.html                               │
           └─ main.tsx → App.tsx                    /api/pokemon   → routes/pokemon.ts
              (React, one page at a time            /api/battles   → routes/battles.ts
               chosen with useState)                /api/pokedex   → routes/pokedex.ts
                     │                              /api/auth/*    → routes/auth.ts → Better Auth
                     │  fetch("/api/...")           /api/docs      → routes/docs.ts (Swagger)
                     └──────────────────────────────►    ...
```

Key facts about the old app:

- **Backend**: Hono routes in `src/routes/*.ts`. Each file exported a function like
  `createPokemonRoutes(database, service)` that built a small Hono router, and `src/app.ts`
  mounted them all with `app.route("/api/pokemon", ...)`.
- **Frontend**: a React app served at `/ui`. There was no router. `App.tsx` kept
  `activePage` in `useState` and used a long `? :` chain to choose which page component to show.
  The URL never changed when you clicked around.
- **Talking to the API**: hand-written `fetch` wrappers in `src/frontend/api/*.ts`. Each one
  set headers, handled timeouts with `AbortController`, parsed JSON, and turned errors into
  messages. The response types (`PokemonDetail`, `FightResult`, ...) were typed by hand and could
  drift away from what the server actually sent.
- **API docs**: `src/docs/openapi.ts`, an 856-line hand-written OpenAPI document.

## What the new app looks like

The new app is **one TanStack Start application**. Vite runs it in development; it builds to a
single server for production.

```
                        TanStack Start (vite dev / vite build)
                                     │
        ┌────────────────────────────┼──────────────────────────────────┐
        │                            │                                  │
  Page routes                  API server routes                 Better Auth
  src/routes/*.tsx             src/routes/api.$.ts      (REST)    src/routes/api/auth/$.ts
  /, /pokemon, /search,        src/routes/api.rpc.$.ts  (RPC)
  /battles, /pokedex                 │
        │                            ▼
        │                   oRPC router  (src/orpc/router/*.ts)
        │                   procedures with input/output schemas
        │                            ▲
        └── useQuery(orpc.pokemon.get.queryOptions(...)) ─── typed client (src/orpc/client.ts)
```

Key facts about the new app:

- **Backend**: oRPC *procedures* in `src/orpc/router/*.ts`. Each procedure declares its HTTP
  method and path, its input schema, its output schema, and a handler.
- **Two ways to call the same procedure**:
  - REST, at the **same URLs as before** (`GET /api/pokemon/pikachu`), for Postman, PowerShell
    and Swagger.
  - RPC, at `/api/rpc/...`, used by the React pages through a **typed client**. The frontend
    calls `client.pokemon.get({ identifier: "pikachu" })` and TypeScript knows the exact shape of
    the result, because it comes from the server's output schema.
- **Frontend**: real pages with real URLs (`/pokemon`, `/battles`, ...) using TanStack Router.
  Data loading uses TanStack Query instead of `useEffect` + `fetch`.
- **API docs**: generated automatically from the procedures' Zod schemas.

## Technology swap table

| Concern | Old (`../pokedex`) | New (this project) |
| --- | --- | --- |
| Runtime / dev server | Bun (`bun --hot src/server.ts`) | Vite via TanStack Start (`vite dev`) |
| HTTP routing for the API | Hono | TanStack Start server routes + oRPC |
| Request validation | `@hono/zod-validator` and manual `safeParse` | oRPC `.input(zodSchema)` |
| Response typing | Not checked | oRPC `.output(zodSchema)` |
| Errors | `app.onError` + `c.json({ error }, status)` | oRPC middleware + `throw new ORPCError(...)` |
| API docs | Hand-written `src/docs/openapi.ts` + `@hono/swagger-ui` | Generated by oRPC's `OpenAPIReferencePlugin` |
| Frontend serving | Bun HTML import at `/ui` | TanStack Start with SSR at `/` |
| Page navigation | `useState<PageId>` | TanStack Router file routes |
| Data fetching | Hand-written `fetch` wrappers | oRPC client + TanStack Query |
| Auth calls from the browser | `fetch("/api/auth/sign-in/email")` | Better Auth's `authClient.signIn.email(...)` |
| PostgreSQL driver | `drizzle-orm/bun-sql` | `drizzle-orm/node-postgres` (`pg`) |
| Styling | Plain CSS | Same plain CSS + Tailwind utilities + shadcn/ui components |

## What did *not* change

This is just as important as what did change:

- The database schema and all 13 migrations in `drizzle/`.
- The business logic: the Pokémon cache, PokeAPI calls, battle scoring, type matchups.
- The REST URLs and HTTP status codes. Old PowerShell scripts and Postman requests still work.
- The look of the app. The CSS was copied over.
- Better Auth, Drizzle, Zod, ky, date-fns and T3 Env are all still used.

## Why migrate at all?

1. **One source of truth for types.** In the old app, the server's response shape and the
   frontend's `type PokemonDetail = {...}` were written separately. With oRPC, the frontend's
   types come *from* the server code, so a mismatch becomes a TypeScript error instead of a bug.
2. **Less hand-written plumbing.** The `fetch` wrappers, the abort/timeout/loading/error
   `useState` juggling, and the 856-line OpenAPI file were all replaced by library features.
3. **Real URLs.** You can bookmark `/battles`, use the back button, and share links.
4. **Server rendering.** The first page load arrives as HTML.
